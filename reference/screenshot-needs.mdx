The docs should not invent product screenshots. Capture the items below from a clean local or staging deployment when you have a safe demo config with no live secrets, private hostnames, private prompts, or unreleased run data visible.

## Required runtime screenshots

| Page or guide | Capture needed | Why it matters |
|---|---|---|
| [Quickstart](/quickstart) | Dashboard at `http://127.0.0.1:8787/dashboard` after saving a local bearer token | Shows beginners what a successful local smoke-test dashboard looks like |
| [Dispatch flow](/guides/dispatch-flow) | A dry-run dispatch response with no live launch | Demonstrates safe candidate inspection before enabling live dispatch |
| [Dispatch flow](/guides/dispatch-flow) | A blocked dispatch/status response | Shows operators how blockers appear before they troubleshoot |
| [Wake gate](/concepts/wake-gate) | Worker dashboard or run detail showing a quiet-window / `wake_ready`-style state | Makes process and telemetry gating concrete without overexplaining it in prose |
| [Paper artifacts](/guides/paper-artifacts) | Paper review queue row before and after checklist updates | Shows the human review step that prevents generated drafts from being mistaken for publications |
| [Authorship](/reference/authorship-provenance) | Example artifact folder with `paper.md`, `claim_ledger.json`, `evidence_bundle.json`, and `paper_manifest.json` | Reinforces that generated reports travel with provenance artifacts |

## Redaction checklist

Before adding any screenshot:

- Hide bearer tokens, API keys, Notion IDs, private hostnames, private IPs, local usernames, and browser profile data.
- Use demo project names rather than private research prompts or personal notes.
- Prefer cropped UI areas over full-desktop screenshots.
- Keep AI-generated paper text visibly labeled as generated and not peer-reviewed.
- Store image files under `images/` with descriptive names such as `dashboard-local-smoke-test.png`.

## Diagram needs

A simple architecture diagram would help the introduction and control-plane pages. It should show only sourced system boundaries:

```text
LLM scout / Notion intake
  -> Enoch control plane
  -> worker wake gate
  -> Codex/OMX run workspace
  -> evidence + claim ledger
  -> generated artifact + human review
  -> corpus export
```

Use a diagram when it clarifies the flow. Do not add decorative generated images that imply screens or capabilities the repo does not ship.
