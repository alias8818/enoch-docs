Enoch produces research artifacts automatically from the evidence a research agent accumulates during a run. Understanding what those artifacts are, who is responsible for them, and how to cite them correctly is essential before you publish or share any output from the system.

<Warning>
Do not claim human authorship of papers or scientific arguments generated by Enoch, and do not represent generated artifacts as peer-reviewed publications. The system operator is the release maintainer, not the intellectual author of the generated prose or claims.
</Warning>

## What Enoch-generated research artifacts are

When an agent run reaches a `finalize_positive` decision, the control plane creates a set of structured artifacts under `papers/{run_id}/` inside the project directory:

| Artifact | Path | Description |
|---|---|---|
| Draft paper (Markdown) | `papers/{run_id}/paper.md` | AI-written prose synthesised from the evidence bundle and claim ledger |
| Draft paper (LaTeX) | `papers/{run_id}/paper.tex` | LaTeX-formatted equivalent of the Markdown draft |
| Evidence bundle | `papers/{run_id}/evidence_bundle.json` | Raw evidence collected during the run: telemetry, result files, project decision |
| Claim ledger | `papers/{run_id}/claim_ledger.json` | Structured list of claims extracted from the evidence, with limitation notes |
| Paper manifest | `papers/{run_id}/paper_manifest.json` | Provenance metadata: `paper_id`, `generated_at`, and artifact paths |

These artifacts are generated from automated run notes, evidence bundles, claim ledgers, and run metrics that the agent wrote during execution — not from human research activity.

## Who should be credited

The source file for this project's release policy states the following:

<Note>
The reports produced by this system are AI-generated research artifacts created from automated run notes, evidence bundles, claim ledgers, and run metrics. The maintainer releases the corpus for inspection and critique but does not claim personal authorship of the generated papers, arguments, or prose.
</Note>

In practice this means:

- **System operator / release maintainer** — the person who configured and runs the Enoch control plane. Credit them as the operator who released the corpus.
- **Not a human author of the papers** — the operator did not write the prose, arguments, or claims. The AI pipeline did, grounded in the evidence the agent produced.
- **Not peer-reviewed** — generated artifacts have not been submitted to or accepted by any peer-review venue unless you have done so separately after quality-gate approval.

When you release a corpus, use the recommended language from the source file verbatim or adapt it to your context. Do not omit the disclaimer.

## The claim ledger

The claim ledger (`claim_ledger.json`) is the authoritative record of what Enoch asserts in a generated paper. It contains:

- A `claims` array: each entry records a specific, evidence-grounded assertion made by the paper writer.
- A `limitations` array: explicit statements about what the claims do not cover, what evidence is absent, and where human review is required.

You should read the claim ledger before approving any paper for finalization. A deterministic fallback draft (produced when the AI writer is unavailable or `paper_writer_fallback_enabled` is `true`) will contain an empty `claims` array and a limitation noting that human review and richer claim extraction are still required.

## Provenance metadata in `paper_manifest.json`

Every generated paper includes a `paper_manifest.json` file. At minimum it contains:

```json
{
  "paper_id": "<project_id>:<run_id>:arxiv_draft",
  "generated_at": "<ISO-8601 UTC timestamp>"
}
```

The `paper_id` is a compound key that ties the artifact to the specific project and run that produced it. The `generated_at` field records when the control plane wrote the artifact. When you publish or archive a paper, preserve the manifest alongside the draft so downstream readers can trace the artifact back to its source run.

The control plane also embeds a `publication_policy` block in the paper writer context during a rewrite:

```json
{
  "ai_generated": true,
  "operator_credit_claim": "none",
  "disclaimer": "AI-generated and AI-written from automated research artifacts; released with no personal authorship credit claimed by the operator."
}
```

This policy block is recorded in the `paper_review.draft_rewritten` event in the audit log, so it is traceable through `GET /control/api/events`.

## Quality gates before publication

The control plane enforces a publication review workflow before any artifact can be marked `finalized`. You must progress a paper through the following gates using the paper review API:

1. **Evidence present** — if `paper_evidence_sync_enabled` is `true`, the rewrite endpoint (`POST /control/api/paper-reviews/{id}/rewrite-draft`) will refuse to proceed (`424`) if no local evidence is present after attempting an evidence sync from the worker. This ensures the paper is grounded in real run artifacts.

2. **Checklist completion** — each paper review item has a checklist. Every required checklist item must reach `pass` or `accepted_risk` status before approval, except for the `final_human_approval` item, which must reach `pass` specifically — `accepted_risk` is not permitted for that item. You update individual items with `POST /control/api/paper-reviews/{id}/checklist/{item_id}`.

3. **Review status progression** — a paper must pass through `triage_ready` → `in_review` → `approved_for_finalization` before you call `POST /control/api/paper-reviews/{id}/approve-finalization`. You can block a paper at any stage by setting `review_status` to `blocked` and recording a `blocker` reason.

4. **Finalization package** — after approval you can call `POST /control/api/paper-reviews/{id}/prepare-finalization-package` (with `dry_run: false`) to assemble the artifact bundle before external publication.

<Tip>
Use `GET /control/api/paper-reviews/next?paper_status=publication_draft` to find the highest-ranked paper currently ready for review. The rank score is computed from evidence quality signals and checklist progress.
</Tip>

The deployment guide states: "Do not publish generated artifacts until the corpus quality gates pass."
