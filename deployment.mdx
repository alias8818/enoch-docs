A production Enoch deployment splits responsibility across two machines: a control VM that hosts the FastAPI control plane, dashboard, queue state, paper review APIs, alert timer, and corpus tooling; and a worker machine that hosts the wake gate used by OMX/Codex runs, tracks process trees and telemetry, and stores project workspaces and evidence. This guide walks you through every step, from prerequisites to smoke-testing the live API. A single-machine development deployment is also possible — run both services on localhost and set `worker_wake_gate_url` to the same host.

## Prerequisites

<Tabs>
  <Tab title="Control VM">
    Install the following on the control VM before proceeding:

    - Linux with systemd
    - Python 3.11+
    - `uv`
    - `git`
    - Network access to the worker machine
  </Tab>
  <Tab title="Worker machine">
    Install the following on the worker machine before proceeding:

    - Linux with systemd
    - Python 3.11+
    - `uv`
    - `git`
    - OMX/Codex CLI stack used for agent execution
    - Optional: NVIDIA telemetry libraries for GPU visibility
  </Tab>
</Tabs>

## Deployment steps

<Steps>
  <Step title="Clone and install on each machine">
    Run the following commands on both the control VM and the worker machine. For forks, replace `alias8818` with your GitHub owner.

    ```bash
    sudo mkdir -p /opt/enoch-agentic-research-system
    sudo chown "$USER":"$USER" /opt/enoch-agentic-research-system
    git clone https://github.com/alias8818/enoch-agentic-research-system.git /opt/enoch-agentic-research-system
    cd /opt/enoch-agentic-research-system
    uv venv --python /usr/bin/python3 .venv
    uv pip install --python .venv/bin/python -e .
    uv run pytest -q
    ```
  </Step>

  <Step title="Configure the control VM">
    You can use the helper script to install dependencies, copy the checkout into `/opt`, create config and state directories, and install systemd units in one step:

    ```bash
    sudo scripts/install-control-plane.sh
    ```

    For manual setup, create the config and state directories and copy the example config:

    ```bash
    sudo mkdir -p /etc/enoch /var/lib/enoch-control-plane
    sudo cp /opt/enoch-agentic-research-system/config.example.json /etc/enoch/config.json
    sudo editor /etc/enoch/config.json
    ```

    Set at minimum the following required fields in `/etc/enoch/config.json`:

    ```json
    {
      "listen_host": "0.0.0.0",
      "listen_port": 8787,
      "state_dir": "/var/lib/enoch-control-plane/state",
      "project_root": "/var/lib/enoch-control-plane/projects",
      "dispatch_script_path": "/opt/enoch-agentic-research-system/deploy/enoch_omx_dispatch.sh",
      "omx_inbound_bearer_token": "generate-a-long-random-token",
      "completion_callback_url": "https://automation.example.com/webhook/omx-wake-ready",
      "completion_callback_token": "generate-a-long-random-token",
      "worker_wake_gate_url": "http://worker.example:8787",
      "worker_wake_gate_bearer_token": "worker-api-token"
    }
    ```

    <Warning>
      Generate `omx_inbound_bearer_token` and `completion_callback_token` with a cryptographically secure generator. Never reuse tokens across deployments and never commit live config files or credentials.

      ```bash
      python3 - <<'PY'
      import secrets
      print(secrets.token_urlsafe(48))
      PY
      ```
    </Warning>
  </Step>

  <Step title="Configure the worker machine">
    Use the helper script to install dependencies and write a worker-focused example config:

    ```bash
    scripts/install-worker.sh
    ```

    For a minimal manual worker config, copy `config.example.json`, then set `state_dir`, `project_root`, and `omx_inbound_bearer_token`, and run the service on port `8787`.

    The control VM uses the following settings to communicate with the worker:

    - `worker_wake_gate_url` — the URL of the worker API
    - `worker_wake_gate_bearer_token` — the token for authenticated worker checks
    - `paper_evidence_sync_*` settings — used when importing evidence from worker project folders before artifact generation
  </Step>

  <Step title="Install the systemd service on the control VM">
    Copy the service unit, reload systemd, enable and start the service, and confirm it is running:

    ```bash
    sudo cp /opt/enoch-agentic-research-system/deploy/omx-wake-gate.service /etc/systemd/system/enoch-control-plane.service
    sudo systemctl daemon-reload
    sudo systemctl enable --now enoch-control-plane.service
    sudo systemctl status enoch-control-plane.service
    ```

    Check the health endpoint:

    ```bash
    curl -fsS http://127.0.0.1:8787/healthz
    ```

    Open the control plane dashboard in your browser. Use `omx_inbound_bearer_token` as the login token:

    ```text
    http://<control-vm>:8787/control/dashboard
    ```
  </Step>

  <Step title="Enable Pushover queue alerts (optional)">
    Pushover is optional but recommended for alerting on queue hangs or stoppages. Add the following fields to `/etc/enoch/config.json`:

    ```json
    {
      "pushover_alerts_enabled": true,
      "pushover_app_token": "your-pushover-application-token",
      "pushover_user_key": "your-pushover-user-key",
      "queue_alert_cooldown_sec": 1800,
      "queue_alert_hang_after_sec": 3600
    }
    ```

    Install the alert timer:

    ```bash
    sudo cp /opt/enoch-agentic-research-system/deploy/enoch-queue-alert-check.service /etc/systemd/system/
    sudo cp /opt/enoch-agentic-research-system/deploy/enoch-queue-alert-check.timer /etc/systemd/system/
    sudo systemctl daemon-reload
    sudo systemctl enable --now enoch-queue-alert-check.timer
    systemctl list-timers enoch-queue-alert-check.timer
    ```

    To trigger a manual alert or preflight check:

    ```bash
    sudo OMX_WAKE_GATE_CONFIG=/etc/enoch/config.json /opt/enoch-agentic-research-system/deploy/enoch_queue_alert_check.py
    ```
  </Step>

  <Step title="Smoke-test the core API paths">
    Read the token from your config and run the status and preflight checks:

    ```bash
    TOKEN=$(python3 - <<'PY'
    import json
    print(json.load(open('/etc/enoch/config.json'))['omx_inbound_bearer_token'])
    PY
    )

    curl -fsS -H "Authorization: Bearer $TOKEN" \
      http://127.0.0.1:8787/control/api/status | python3 -m json.tool

    curl -fsS -H "Authorization: Bearer $TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"wake_gate_url":"http://worker.example:8787","bearer_token":"worker-api-token","require_paused":false,"strict":false}' \
      http://127.0.0.1:8787/control/api/preflight | python3 -m json.tool
    ```

    Run a dry-run dispatch to check dispatch readiness before sending real work:

    ```bash
    curl -fsS -H "Authorization: Bearer $TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"dry_run":true,"requested_by":"operator"}' \
      http://127.0.0.1:8787/control/dispatch-next | python3 -m json.tool
    ```
  </Step>

  <Step title="Review the dispatch flow">
    Every live dispatch request passes through the following checks in order. Understanding this sequence helps you diagnose failures at each stage:

    1. No conflicting active GPU lane exists (single active lane enforced).
    2. A queue item exists.
    3. Live dispatch is enabled (`live_dispatch_enabled` must be `true` in config).
    4. The control plane is not paused and maintenance mode is not active (checked together).
    5. Worker preflight is healthy.
    6. The dispatch script launches the agent run.
    7. The wake gate tracks process and telemetry truth.
    8. The completion callback or status update is emitted only after the gate is satisfied.

    <Tip>
      Always use dry-run dispatch first when testing a new deployment. It exercises the core dispatch guards — pause checks, lane safety (single active GPU lane), and candidate selection — without launching a real agent run. Note that worker preflight is only performed during live dispatch, not dry-run.
    </Tip>
  </Step>

  <Step title="Configure the paper artifact workflow">
    The control plane can rewrite and package generated research artifacts when paper rows and evidence are present. Add the following settings to `/etc/enoch/config.json` to enable the artifact writer with the recommended Synthetic.new / GLM-5.1 provider:

    ```json
    {
      "paper_writer_provider": "synthetic.new",
      "paper_writer_base_url": "https://api.synthetic.new/openai/v1",
      "paper_writer_model": "hf:zai-org/GLM-5.1",
      "paper_writer_api_key": "your-provider-key",
      "paper_writer_fallback_enabled": true,
      "paper_evidence_sync_enabled": true
    }
    ```

    <Warning>
      Do not publish generated artifacts until the corpus quality gates pass. The quality gates scan for placeholder citations, missing provenance, and missing evidence artifacts before allowing anything to enter the corpus.
    </Warning>
  </Step>
</Steps>

## What is not included

This repository does not include live secrets, private production config, generated paper corpus artifacts, old workflow-tool exports, private run state databases, or production logs. Those are intentionally excluded. Use the example config and this guide to recreate a clean deployment from scratch.
